| Starts each MCP server in a process group of its own, so killing the agent's group left them running under PPID 1 | `host/src/agent/process.rs`: the agent leads a session of its own (`own_tree`), and stopping it ends every group in that session (`end_groups` in `process_unix.rs`) | none: a program may lead a group of its own | Keep: it also covers any MCP server that does the same |

| `session/new` can't start an ephemeral thread (codex-acp keeps those for its own titles), so a background job's session (dreaming, naming, call titles) is saved like a chat and lists in the user's Codex and ChatGPT history (Codync #346) | `host/src/chat/oneshot.rs`: `session/delete` when the job ends, which codex-acp turns into `thread/archive`: the thread leaves the history, its rollout file stays under `~/.codex/sessions` | none: ACP has no ephemeral option on `session/new` for codex-acp to take | `session/new` takes an ephemeral option: start the job's session with it and drop the delete |

## Fork

Checked 2026-11-15 for threads ([spikes](../archive/background-tasks-plan-2026-11-15.md#spikes)). codex-acp 2.6.0 on Codex CLI 0.167.0 (`npx -y @agentclientprotocol/codex-acp@2.6.0`, model `gpt-6.1-sol`) advertises `sessionCapabilities.fork: {}`, which the host reads (`host/src/agent/bot/launch.rs`). `session/fork` from a second process, right after the first one's turn and while it still held the session, returned a new session that knew the chat; the original never saw what the fork was told after. No history is replayed. The fork's first turn read 7,168 of 25,728 input tokens from the cache (the chat's one turn before it had written none yet); its second read 25,600 of 25,751. Through the host (2026-11-16, an isolated host on the default login, two agents at once): a bot added two tasks, both threads began with `start: fork` with Codync's MCP servers and instructions, the chat answered in between, and both reports came back.
