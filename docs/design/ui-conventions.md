# UI conventions

## iPhone navigation

The bot list and conversation use the system `NavigationStack` toolbar. `ToolbarItem` owns the account button and, at the trailing end as on the desktop's list header, the filter button (`line.3.horizontal.decrease`, filled while a computer is left out: the list's options first, as on the desktop, **Group by computer** (default on; off, several computers' bots are one list without headings) and **Sort by status** (default off; needs you, working, waiting work, the rest; no drag while on), both kept on the device (`ListLayout`), and **Sort by last active** (the shown online computers' host-synced [Move active bots to the top](../features/computer-order.md), only while one has it); then the computers to show, Reconnect, Manage computers; `list_layout_changed` on each switch), Search (the native search field under the bar, finding bots by name across the shown computers, flat) and New (New bot, New group chat). The title is Bots with how the shown computers are connected as its subtitle (`1 connected`). The list's top edge is the soft scroll-edge effect (`.scrollEdgeEffectStyle(.soft, for: .top)`), as in the conversation, not the plain `List`'s hard bar. Android draws the same header with glass buttons and its own search field. The conversation copies Grok Bot: the title (the bot's avatar and name) is a plain button that opens its details sheet on Details, a group's editor for a group (VoiceOver: "<name>, view details"); the other bot actions live where the desktop has them (Pin, New session (bots only, after a confirm), Make lead agent and Delete in the bot list's touch-and-hold menu, one list with no dividers, Full conversation through a message's Show what it did, Reconnect through pull to refresh and the computer menu), the trailing buttons are find (magnifying glass; it opens the find bar floating under the toolbar like the call bar, the message with the shown match tinted and scrolled into view) and the computer (remote screen; it pulses while this bot operates the screen), the same two as glass buttons in Android's header, and the call button sits in the composer as a filled waveform capsule while the box is empty. Menus opened from toolbar buttons (New, the computer filter) are native `Menu`s, like every iOS menu; the conversation uses the system back button. iOS supplies Liquid Glass, control sizing, grouping and interaction feedback.

iOS presents through `.codyncSheet` or `.codyncOverlay` (`Chrome.swift`), and what the system draws (`.photosPicker`) through `.quietPresentation`, which would freeze content of our own; never a raw `.sheet`, `.fullScreenCover` or `.photosPicker`. Any of those running again with a render re-sends what's presented, which rebuilds a system menu open there (its icons resolve anew), and a press during the rebuild is lost. `.fileImporter` hasn't been measured and stays raw. Two menus still rebuild with the list: the roster toolbar's computer and New menus, raw `Menu`s outside `MenuRows` (New's lost taps aren't measured).

The conversation keeps the native glass buttons over the chat with a soft top scroll-edge effect, so messages blur out under the header instead of running sharp behind it. Root error dialogs use an in-place, full-screen scrim so presenting them does not change the underlying glass controls' appearance.

iPhone conversation scrolling leaves dragging, deceleration, and bottom rubber-band return to UIKit. Passive bottom-following must not move the offset during those gestures, and returning from bottom overscroll does not count as reading history or show Jump to latest. Desktop keeps browser scrolling; the terminal uses line-based scrolling, so neither shares this UIKit-specific behavior.

Do not wrap those toolbar controls in `IconButtonStyle`, hand-sized rounded backgrounds or another glass effect. The account avatar is toolbar content, with the system supplying the enclosing surface. This is the explicit exception to the custom-chrome rule below.

Connecting and reconnecting are background work. `BotStore` gives initial offline reports 1 second to recover and holds drops from online (including relay "computer offline" reports) for 5 seconds. "No access" shows immediately. Automatic read acknowledgements never open an error dialog and visible conversations are acknowledged again after reconnecting. An action taken during a reconnect (back in the foreground, a new network, a drop still inside its grace) waits for the link, up to 20 seconds, instead of failing; while one waits, headers read `Connecting…` and the conversation's connection label shows a spinner. Calls that are safe to repeat (send, stop, approvals, pin, hide, mark as read, delete) are tried again when the link drops under them. Tapping while the header says Offline because the computer can't be reached starts a fresh connection attempt and waits for it, instead of failing until the backoff gets there; a computer the relay reports as off fails at once, since the relay says when it is back, while one the relay is waking (a cloud computer asleep) is waited for like a reconnect. A permission card shows a spinner on the chosen option, dims the others and takes no second answer until the computer has it. The desktop app's `BotStore` (link handling in `apps/desktop/src/renderer/store/bot-sync.ts`) applies the same graces and 20-second wait. The TUI follows the same rule over loopback: a command the host can't be reached for is retried for up to 20 seconds behind its "Reconnecting…" indicator (the `hello` probe that explains an unreachable host still answers at once), and its permission cards spin on the chosen option. The "Something went wrong" dialog is left for a computer that is off, a refused device, the computer's own answers, and reconnects that outlast the wait. Background work (cloud refresh, device registration) logs connection, busy-cloud and stale-token failures instead of showing them. The iOS app disconnects only in `.background`, not `.inactive`. Connection status lives only in headers and their menus. The roster header shows a small summary (`1 connected`, `1/2 connected`, `2 offline`, `Connecting…`, or `Waking the computer…` for a cloud computer on its way up). Its computer menu supports multiple selections (picking a computer or All computers leaves the menu open for the next pick), reconnect, and management. At least one available computer stays selected; if saved exclusions would hide every computer, the list falls back to all. Filters persist on the device. Bots sort in bands, the [lead bot](../features/lead-bot.md) (crowned on the desktop; never dragged while **Freeze the lead bot at the top** is on) first, then pinned bots, then the rest; within a band, in the order the user dragged them into, then by recency ([bot order](../features/computer-order.md#bot-order)). Bots the user put in a section sit under a foldable section heading (name, count, and the unread total while folded, amber while it counts an approval card waiting on the user; folded state saved on the device), with sections and the plain "Bots" group in device-local order after pinned bots (initially sections sorted by name, then Bots). A bot's long-press menu has Move to section (not the lead's); a heading's has Rename section and Remove section; a move or rename the computer refuses is put back. On iPhone, when more than one computer is shown, each computer gets a light heading (badge, name, connection, and "No bots yet" when empty) above its own bots; with one computer the list stays flat. Tapping a heading folds that computer's bots away (chevron; saved on the device). Long-press a heading to drag the computer with its bots up or down: while it is lifted every computer's bots fold into their headings, they unfold on release, and the order is saved on the device (`AccountStore.move`; VoiceOver: Move up / Move down). A bot moves only among its own computer's bots, within its band, and an unpinned bot only inside its section (pinned bots ignore sections). The desktop app's sidebar has the same headings, folding and heading drag (a lifted copy follows the pointer, plus Alt+Up/Down), and the same section headings. There are no connection banners. The compact desktop rail uses a computer icon for the same menu. While a computer's visible bots run more than one agent, each bot row marks its avatar's bottom-left corner with the logo of the agent it runs on right now (a fallback's while on one; groups get none); **Show agent logos** in Settings › Appearance (desktop: General › Appearance; each device's own, on by default) turns it off. The TUI shows no logos (a terminal can't draw them, and letters would be ambiguous: Claude Code, Codex, Cursor and Copilot all start with C). Conversation headers show a small connection label; the desktop names the computer in its help text, the phones in the bot details' Settings (Workspace → Computer). Pull-to-refresh remains available on iPhone. Computer setup and access requests live under Manage computers; a phone asks an account computer for access only when the user taps Ask for access, never on its own.

Sources: `apps/ios/Views/BotListView.swift`, `AccountSwitcherView.swift`, `apps/ios/Kit/Sources/CodyncUI/Chat/ChatView.swift`, `Bots/ComputerFilterHeader.swift`, `Store/ComputerSelection.swift`, `Bots/BotRow.swift`; desktop: `apps/desktop/src/renderer/views/ChatWindow.tsx`, `ComputerFilterHeader.tsx`, `BotRow.tsx`.

## Desktop menu bar (tray)

The iPhone App Store update reminder uses a hierarchical `arrow.down.circle.fill`
symbol in the primary text color, keeping the download arrow clear against its
softer circle in both appearances. Desktop updates live in Settings and the native
tray menu; the TUI uses a text action and status message. Neither has this App Store
reminder card, so its decorative icon treatment is iPhone-only.

Release update controls live in the tray's Settings → Updates submenu; the chat
window's Settings has the same controls on its Updates page. One action carries the
whole flow (`apps/desktop/src/shared/update-action.ts`, the same label in the tray, the
Updates page and the update-needed card): **Check for updates** → **Update to <version>**
→ **Downloading… N%** (the Updates page adds a progress bar) → **Restart to update** →
**Restarting…**. A check the person starts that finds nothing opens a **You're up to date**
dialog in the chat window (scheduled checks stay silent). A finished download never quits the app on its own; the person restarts,
or it installs once idle (once no bot is working, when another device chose **Update now** for
this computer). While a release is available, a filled arrow badge sits on the
window's rail above the account avatar, its tooltip the same action label; one click
restarts into the release, downloading it first if needed (a ring fills with the download
while the app stays usable, then a spinner while it restarts), and it is gone once the app
runs the latest version. The TUI action list has **Check for updates**. Download and
install go through electron-updater (`apps/desktop/src/main/updates.ts`); there is no
separate update window.

The tray menu is Electron's native `Menu` (`apps/desktop/src/main/tray.ts`), the only system menu in the desktop app. Its commands, submenus, checkboxes, usage-icon radio items, separators and keyboard navigation use system styling. Do not add custom cards, hover backgrounds, icon buttons or a window-style menu panel here. Action rows (Open, Pair phone, host actions, approval review, Remote screen, Settings, Quit) carry an SF Symbol: on macOS through `nativeImage.createMenuSymbol`, on Linux and Windows as the symbol's Lucide fallback the renderer draws (`TRAY_SYMBOLS`, `tray-summary.ts`). The Network row carries the codync-network mark instead, as in the app (SF Symbols has none): the renderer draws it on every platform, a template image on macOS. A computer's row in the usage limits carries the SF Symbol for what it is (a desktop for Linux: SF Symbols has no penguin, which only the app's badge draws). Status, bot and the other usage rows get none. The app version is a row in Settings → Updates, so Settings and Quit end the menu together.

The menu retains host installation/restart, bot conversation/stop actions, approval review, usage limits, remote-screen permissions, open-at-login and quit. Pairing opens a separate titled window because its QR needs a persistent scanning surface. The chat window retains its own UI conventions.

Usage limits appear directly in the top-level menu, grouped by provider with native section headers. Show each window's used percentage (`{percent}% used`), reset time when available, and the provider's last update; do not hide them in submenus. The chat window's
Usage page, an entry of its rail, shows the same per-provider bars. That page and the phones' Usage screen show one card a computer, and a button beside its name swaps the bars for the computer's agents with a drag handle and a switch each ([which agents show](../features/usage-limits.md#which-agents-show)).

## The window's rail and Settings (desktop)

The chat window's leading edge is a 64-point rail of icon entries, each a page of the window: Bots, Threads, Workflows (while a computer offers them), Computers, Network, Extensions and Usage, then at its bottom Settings (a gear) and the account's avatar, which opens the account's menu: who is signed in, **Sign out** and **Delete account**, or the ways to sign in (`NavRail.tsx`). The rail and the bar across the top share one color a step off the list column's (`--window-chrome`), and the same color runs in a thin strip down the window's trailing edge and along its bottom, so the page (list and content) sits in them as one card with round corners. Across the top of the window a bar moves it and holds Back and Forward (the pages shown, and on Bots each bot), the list's toggle, and at its trailing end, for the conversation shown, its bot (the title pill), what runs it (a click shows the bot's Settings) and the panel's toggle (`WindowBar.tsx`; the conversation puts its part there). The Bots, Threads and Workflows lists each have a round filter button in their header (marked while a computer is filtered out; on Workflows its menu holds only the computers to show); its menu holds **Group by computer** and **Sort by status**, on Threads first **Group by bot** (one grouping at a time there), on Bots also **Sort by last active** (the shown computers' own [Move active bots to the top](../features/computer-order.md), so it reaches every device) and **Freeze the lead bot at the top** (this device's own: the [lead bot](../features/lead-bot.md) keeps the very top of the list, the Threads list's grouping following it), then the computers to show with each one's connection; the first two are kept per list on the device: Bots starts grouped by computer, Threads sorted by status; grouped, a heading is a computer, and sorted, what needs you comes first. Changing how a list is grouped or sorted slides each row from where it was to its new place on the theme's spring (a row that wasn't there fades in; `useListFlip` in `lib/slide.ts`), and a reorder within a section slides the same way (`useSlide`). Bots, Threads and Workflows show a list beside their content; their entry pressed again folds that list away and brings it back, as does **Toggle Sidebar**. The other entries fill the window. Threads carries the count of items being worked on, Computers the count of devices waiting to be let in. A conversation left for another page stays as it was. **Settings** is laid out like ChatGPT's desktop settings (references in `reference/chatgpt-settings-*.png`): a sidebar of pages under small group labels (Personal: General, Voice chat; This Mac, or This computer on Linux: Computer access, Updates) and a large page title over the page's sections. Computers, Network and Usage are pages of the same kind under their own rail entries, shown without that sidebar. General's Account card holds **Sign out**, and its Support card Help & documentation, Report an issue and Get Codync for mobile. Approval badges lead to the Computers page, where each computer's row also has **Reconnect**; the lists' filter menu only filters. The phone apps' Settings tab (iPhone and Android), to the right of Workflows in the same bar, holds only what belongs to the phone itself: Show status (widgets, Live Activity and the Dynamic Island), appearance, language, thinking details, notification permission, usage analytics and Start over. Anything that belongs to one computer lives in Computer management, the sheet Manage computers and links open: one card per computer with its name and status, then Extensions, Voice chat (its keys live on that computer), Screen, Push notifications (whether that computer alerts this phone), Connection and Codync as rows (Connection shows the route's short name, its menu the whole route; Codync shows the version the computer runs, whether it's up to date, and **Update** when a newer release is out or this app needs one), then Hidden bots, and Pair a computer in a card of its own. The desktop's Computers page shows the same Codync row on each SSH computer's card, and on this computer's on Linux (on macOS and Windows this computer's Codync is the app, on the Updates page). Source: `apps/desktop/src/renderer/views/settings/SettingsView.tsx`, the rail in `apps/desktop/src/renderer/views/NavRail.tsx`.

## iPhone and desktop code

The iPhone and the desktop no longer share UI code. `CodyncUI` (`apps/ios/Kit/`) is the iPhone app's own package; the desktop app (`apps/desktop/src/renderer/`) is a TypeScript port of the same screens with its own `BotStore`, chat items (`views/chat/chat-items.ts`) and Markdown blocks (`markdown-blocks.ts`).

- The iPhone chat's chrome is in `ChatView.swift` (`body`, `chrome`, `header`). The iPhone conversation is a UIKit collection view of hosted SwiftUI rows (`ConversationList.swift`): it loads earlier messages from the computer as the reader scrolls up, runs under the bars and the composer (the list sits in the safe area and reaches past it, so rows never get a safe area of their own), follows the newest message until they scroll away (with a round "Jump to latest" button), and pops each new message in ([chat messages](../features/chat-messages.md)).
- The desktop UI rules (custom controls, no system menus except the tray, icon-only buttons, fill or border) are implemented in `apps/desktop/src/renderer/components/` (`Controls.tsx`, `Overlay.tsx`, `Menu.tsx`, `Icon.tsx`, `Text.tsx`, `Stack.tsx`); how views use them and the theme tokens: [desktop styles](../guides/desktop-styles.md). Chrome on the sidebar (its header actions, the computer filter, Extensions) is outlined; chrome floating over the conversation (the title pill, the composer) is filled with a shadow, and the composer also carries the floating-layer outline. Corner radii and shadows come from the `--radius-*` and `--shadow-*` scale in `styles/theme.css`. Status text uses `--attention` (`--warning` is for dots and fills only), and destructive fills use `--danger-fill` with `--on-danger`, so both stay readable in light and dark. Sheets and dialogs hold focus while open: the window behind goes inert, Tab cycles inside, and focus returns to where it was on close. With several open at once, only the one drawn on top (a dialog over a sheet) and the menus opened from it take clicks, focus and Escape; the next one down takes over when it closes, and focus goes back to the first one's opener when the last closes.
- The Android app (`apps/android/`) ports the iPhone screens one to one in Compose. Where iOS uses system UI (the tab bar, menus, sheets, Liquid Glass), Android draws the same look with its `design` module: glass from Kyant's backdrop library (blur, lens refraction and highlight on RenderEffect/RuntimeShader), the iOS sheet with its grabber and drag-to-close, glass menus and context menus, Inter for SF Pro and Material Symbols for SF Symbols (`Symbol("sf.name")`), and the soft scroll edge under its bars (`ScrollEdge`: the content behind the header, composer and tab bar blurs and washes out). Android has no Liquid Glass of its own; Material widgets aren't used.
- A change to one lands in the other and the TUI in the same change; see [native client parity](#native-client-parity).

## Shared application controls

Other custom iPhone screens use CodyncUI's `Chrome.swift` and `Controls.swift`, and CodyncKit's `Design/ModalChrome.swift` (`IconButton`, `ModalHeader`), `Design/Cards.swift` (`CardForm`, `CardSection`) and `Design/Spinner.swift`, which live there so the share extension draws like the app. The desktop equivalents are in `Overlay.tsx` (`Sheet`, `Dialog`, `ModalHeader`), `Menu.tsx` (`AnchoredMenu`) and `Controls.tsx` (`IconButton`, `DropdownMenu`, `ChoicePicker`, `ChipChoice`, `Switch`, `CardForm`, `CardSection`, `ValueRow`).

| Need | Component |
|---|---|
| Modal or full-window overlay | `.codyncSheet` (system sheet), `.codyncOverlay` |
| Header outside the native bot navigation flow | `ModalHeader`, `ScreenHeader` |
| Icon action | `IconButton` |
| iPhone app tabs | System `TabView` (Liquid Glass tab bar, hidden inside a chat or a workflow's detail or run): Bots (the desktop rail's bot mark, a template asset `bot`), Threads (`checklist`, with the count of working tasks), Workflows (the desktop's Lucide `workflow` mark, a template asset `workflow`; Android's `workflow` drawable), Settings. State opens from Settings. |
| Menu / confirmation | `DropdownMenu` / `.contextActions` (system menus), `.codyncDialog` |
| Toggle | `ToggleStyle.codync` |
| Form-like content | `CardForm`, `CardSection` (a small bold heading over a filled, rounded group; rows split by inset hairlines; a row is `ValueRow` with an optional one-line `detail`, and its picker is an outlined `ChoicePicker`) |

Avoid adding stock `Menu`, `Picker`, `Form`/`List` styling, switch toggles, alerts, `ProgressView` or system sheets to these flows. The iPhone bot list is a `List` with its styling removed (plain, no separators or row backgrounds), only for the system's drag-to-reorder alongside each row's context menu ([bot order](../features/computer-order.md#bot-order)). The iPhone Usage screen is a grouped `List` for the same reason, in edit mode only while arranging its agents. The iPhone folder picker (`FolderPicker.swift`, one `FolderPage.swift` per folder) is native throughout, the way a system document picker is: a `NavigationStack` inside its `.codyncSheet` (medium and large detents), an inset-grouped `List` with `.searchable`, Cancel (`cancellationAction`) and Use this folder (`confirmationAction`) in the bar with the system's own glass, `ProgressView` while a folder loads, and Browse other folders pushing a page per folder whose title menu (`toolbarTitleMenu`) holds Enter folder path, Parent folder and the ancestors. Android draws the same order with its `design` module. System presentation APIs inside the shared chrome implementation are implementation details, not permission to bypass the components in feature screens. Native WidgetKit/ActivityKit containers and OS authentication/permission flows remain system integrations.

No scroll bars: scroll indicators never show (`.scrollIndicators(.never)` on the iPhone app's root, so every scroll view inherits it; hidden scrollbars in `apps/desktop/src/renderer/styles/theme.css`).

Anything with a background fill gets no extra drawn border. Use `Palette` and `Motion`; visibility changes animate and honor Reduce Motion. Icon-only actions have an accessibility label and desktop help where applicable. Reserve text for actions an icon cannot clearly express.

## Motion and status

`CharacterAvatar` identifies a bot. `ThinkingOrb` conveys working, searching, listening, connecting or shaping as a halftone disc (fixed dots that only change size) and needs adjacent text or an accessible outer label. In-app animation pauses off-screen, when inactive, or with Reduce Motion, on a still pose per state. Widgets/activities use those still poses.

iPhone cold launch: the system launch screen is plain `Palette.background` (`LaunchBackground`), then `LaunchSplash` pops the app-icon bot (squircle, working mood) in while every paired computer connects and finishes its first catch-up (`BotStore.caughtUp`: the `hello` rev reached). It stays at least 0.7 s and at most 1.8 s, then zooms out over the cached list. Without a paired computer (first launch) it is skipped. Android does the same (`LaunchSplash.kt`). The desktop app and TUI reach their host over loopback at once, so they have no splash; while the desktop's own host is still starting, its "Starting the host…" screen (`HostStateView`, full and compact in `StartupRecovery`) shows the same bot popping in and bobbing above the text, still with Reduce Motion.

On iPhone, provider identity and activity presentation are shared with widgets in `CodyncKit/Design`; use those components rather than re-creating mappings per target. The desktop draws them in `components/AgentIcon.tsx`, `Avatar.tsx` and `ThinkingOrb.tsx`. See [mobile widgets](mobile-widgets.md) for current rendering and previews.

The [2026-09-25 audit](../archive/ui-audit-2026-09-25.md) is historical. Its old line numbers and recommendations are not the current UI policy or a list of confirmed open bugs.

Model discovery keeps loading and refresh in one fixed-size slot beside the Model picker. Refresh retains the current catalog while loading, and loading does not add a separate row to the settings card. The Model label keeps its intrinsic width; the model picker takes the remaining width and truncates long names, with the full name available in its tooltip and menu. Fast mode is a separate switch row below it (see [model selection](../features/marketplace.md#fast-mode)).

## Desktop conversation details

Desktop conversations start with the details inspector closed; the title menu opens it on demand. Keep the transcript and composer aligned in one reading column, 820 points wide and scaled with the text size (`--column`). The composer is one box: the field on top, and under it a row of what it sends with: a round `+` (Add files) at the start, then at the end, in a bot's chat, what the conversation runs on as quiet chips (`RunOptions.tsx`; the model's panel is `views/bots/ModelPicker.tsx`), the mic and its engine menu on one shared fill, and send / stop / call. In a bot's chat the chip is its model; on a new thread the bot (or No bot), the folder and the model; in an open thread where it works. The model chip opens a panel, as tall as what it lists, of two columns over a footer: a rail of what it runs on, every agent once per login (`loginSeats`), a login beside the default one with its initials on a badge (a bot's chat and a new thread: the installed agents and their signed-in logins, with the one in use; a bot's chat saves a choice to the bot as its Settings would; a new thread lists each agent's default login only on a host without `hello.threadLogins`; in Settings an agent that isn't installed reads "(not installed)"). The same panel is the bot's Settings' agent picker, each fallback's and the threads' agent's, opened from a full-width row (`trigger="row"`) with the place's notes and fields under the model's settings, ending in a dashed `+` (Add agent) that opens Extensions; the agent's models under a search field, with a spinner while its catalog loads and ⌘1–9 picking the first nine, and what is typed offered as a model ID (an agent that lists no models says so and runs one named by its ID); under the models the effort, its name and level over a track of steps whose knob is dragged along it or a step clicked (or picked with Space or Enter; `views/bots/EffortTrack.tsx`), the steps up to it filled with a fine dot grid, then the model's other settings, each its name, its value and a menu; and a footer of Standard / Fast (where the agent has Fast mode) and how it is approved, a menu at its end. The window's bar keeps only the bot's title pill: what runs the bot is in the box. The phones' composer has the same two layers in its one glass box: the field on top; under it the `+` (a light circle like the mic's capsule), then at the end, in a bot's own chat (not a group's or a thread's), the model chip (on a new thread instead the bot chip and, without a bot, its model chip) (the agent's logo and the model, `ModelChip.swift` / `ModelChip.kt`), the mic and send / stop / call. The chip opens a sheet with the phone's model panel (`ModelPanel.swift` / `ModelPanel.kt`), no title: at the top the agent in use as a chip (logo, login name, a menu of the installed agents' logins, `readySeats` / `readyLogins`, then **Add login profile** for an agent that has them) and a search button that opens a field (what is typed offered as a model ID); the agent's models full width, each its name and the line the agent gives about it, the first six and the rest under **More models** (opened when the one in use is among them; searching lists all), a check and a fill on the one in use, pull down to read the list again; then (hidden while searching, so the list keeps the room the keyboard leaves) one card (`surface` fill) with the effort slider, the model's other settings as menus, **Approvals** (the bot's Permissions, a menu; only from a bot's chat) and **Speed**, a Fast toggle where the agent has Fast mode; the panel's notes under it. Each change is saved to the bot a moment after it's made; the chip is off while the computer is offline. The bot's Settings keep the folding agent picker. The inspector is resized by dragging its edge or with ←/→ while the edge has focus, like the sidebar (`ResizeHandle`); it keeps its width, at least 260 points, leaving the conversation at least 380. The roster selection, composer and outgoing messages have separate surface tokens so selection and input do not compete with the conversation. Roster names use body text and previews use callout text; previews show the first nonempty line without common Markdown heading, quote, bold or code delimiters, matching the terminal roster.

Preserve the original character avatar design: dotted shading, highlight-only color, silhouettes and animation. Desktop roster avatars remain 30 points and iPhone roster avatars remain 46 points. iPhone shares readable secondary text and message previews; its native navigation remains platform-specific. Terminal avatars already use solid color and the terminal has no persistent details inspector; its secondary text uses the same readable palette.

The details inspector (`apps/desktop/src/renderer/views/chat/DetailsPanel.tsx`) opens on the bot's face, name and what runs it, centered at the top - a lead bot's crown there opens the lead agent role explanation, where the roster's crown only marks its row - and has no other header of its own: while it is open the window's bar holds its buttons before the panel's toggle, share (Create template), **Maximize panel** (the panel takes the conversation's place until it is restored) and **Split panel**. Like a thread's panel, it sits beside the conversation whenever both fit (the conversation narrowing to its least, 340 points, for it) and covers the conversation only in a window too narrow for both, Maximize then left out. A thread's panel on the Threads page puts the same buttons in the same order there (`PanelBarButtons`), after the thread's title pill and its status (status word and time); a thread without a bot has no template and one pane, so only Maximize, and Maximize is left out while a window too narrow for the panel beside the thread has it cover the thread already. ## Reading conversations

A visible conversation registers its own read scope while its scene is active. New chat-visible entries (including final updates to an existing message ID) and later roster unread updates acknowledge that scope through the host. Opening the view, returning to the foreground, and reconnecting also acknowledge it. Never gate a receipt on the cached unread count: entry and roster events can arrive separately. Leaving a view or backgrounding the scene unregisters it. The host remains authoritative and broadcasts the resulting unread state to all clients. A pending permission card counts in its chat's unread badge until it is answered, read or not (`Store::badge`; `markRead` changes nothing when only waiting cards are left, so a bot event acknowledges the visible chat only when `unread` is above `waiting`). The bot's `waiting` field says how many of `unread` are such cards: a roster "Mark as read" leaves the count at `waiting`, and a badge with `waiting` above 0 is amber (the avatar's needs-you colour, with black ink on every client). A folded section's heading adds "Needs approval" to its spoken label while one of its bots waits. A phone's bot row speaks its badge (`1 unread`; the iPhone adds "Needs approval", which Android reads from the row's preview).

The iPhone conversation navigation title includes a compact second line with the connection label and the current connection route icon: cloud for Cloudflare, Wi-Fi for direct Wi-Fi/Tailscale. It follows the live route, not the preferred route setting; offline and reconnecting states replace the route icon. VoiceOver also reads the connection description.


## Native client parity

UI changes apply to iOS SwiftUI (`apps/ios/`, `apps/ios/Kit/Sources/CodyncUI/`), the
desktop app (`apps/desktop/src/renderer/`) and the terminal client (`host/src/tui/`)
together. Use each platform's controls while preserving the same actions, information
and states.

- A chat shows the latest non-final agent segment only while its turn is
  working and connected. Earlier narration, tools, empty text and `(pass)` stay out
  of the message list: the running turn's thinking, narration, tool calls (not the
  bot's bookkeeping) and plan appear only in the working pill's unfolded steps, with
  Show thinking details on (Settings › Chat;
  [while it works](../features/chat-messages.md#while-it-works)), and every turn's in
  Full conversation. Completed replies remain visible.
- TUI keeps text and attachments in the composer until sending succeeds. A failed
  send can be retried with Enter; it reuses the nonce. A late response must not erase
  a draft edited while the request was running.
- Connection requests in the chat are cards shaped like an Extensions row (logo, name,
  reason, one action on the right; at most 400 pt wide), with no dismiss button: a
  request just stays until it's done. TUI **C** opens a pending connection request in
  the current lane; selecting a request and pressing Enter opens that request.
  Credentials, connector installation/sign-in and hosted apps use the secure setup
  APIs; Escape closes the editor. Secrets are masked and never sent as chat text. An
  agent sign-in request opens that agent's sign-in sheet instead, which always checks
  the sign-in again.
- A bot-to-bot exchange is a compact centered row ("Messaged [avatar] Owen" / "Message from
  [avatar] Egan"; same verbs for asks; the TUI draws one ` · ` line), never a bubble. Only a
  failure is marked: danger color, a warning mark (triangle icon; the TUI uses a
  glyph), "failed" in the accessibility label. The row
  opens a read-only "A ⇄ B" sheet. In the main chat consecutive exchanges with the same peer
  (either direction; trace entries don't break the run, any other visible entry does) are one
  row, "{N} messages with [avatar] Owen", failed if any failed, keyed by the first exchange
  (TUI: one pick, `c` on it says it is read-only). The sheet matches "Full conversation" (same size;
  `ModalHeader` with the pair, own bot first, as its left title and the close X on the right):
  the pair's whole history as author-labelled grey bubbles (avatar and name above each run),
  time separators after gaps over an hour, "Waiting for {name}…" or the failure detail under
  a pending or failed exchange, no composer. TUI:
  `v`/`r` picks a message, j/k moves to the row, ↵ (or a click) opens it, j/k ↑↓ and
  ^u/^d scroll, esc closes; `r`, `f` and `1…6` on the row say it is read-only. The data contract is
  [bot collaboration](../features/bot-collaboration.md#notice-data).

### iOS jump to latest

A single display-linked motion owns the collection view offset during a requested
jump. Reserve that ownership before updating following, snapshots or keyboard
insets; those updates must not pin the list while the animation runs. Retarget
the current motion as self-sizing rows change the end, without offscreen sizing
jumps or starting overlapping insertion animations. Dragging and scroll-to-top
cancel the jump. Reduce Motion pins directly, and passive following still holds
the newest message at the bottom. Original scroll-edge blur remains unchanged.

This repair targets UIKit's estimated row sizing and collection layout. Desktop
uses DOM scroll geometry and the browser's smooth scrolling rather than the iOS
pre-sizing loop; the terminal jumps by line index without animation. Their current
follow/jump actions remain unchanged.

## Appearance preference

Desktop General → Appearance and phone settings → Appearance offer **System**,
**Light** and **Dark**, defaulting to System. Save the choice on the device,
independently of accounts and hosts, and apply it immediately and on relaunch.
Desktop uses Electron's native theme source so native chrome, CSS and canvas
artwork agree across all windows. iPhone sets the window's interface style so
already-presented sheets update and System clears the override;
Android supplies the selected theme and matching system-bar contrast. Remote
screen viewing and explicitly dark previews keep their existing dark surfaces.

The terminal's `Ctrl+K` actions offer the same three choices, saved in the local
`tui-appearance` file. System retains the terminal's foreground/background and
uses `COLORFGBG` for accent contrast. `CODYNC_THEME` supplies the initial choice
when none is saved; `NO_COLOR` continues to disable color output.

Roster section headings and the Bots label move whole groups within a computer: drag on desktop, touch and hold then drag on phones. Section order is per computer and per device. Pinned bots remain above all groups. Terminal Alt+Up/Down moves the selected bot's group for that run.
