# Conversation runtime

- **Chat ≠ session**: a bot is one endless transcript (SQLite `entries`, ordered by `seq`); the ACP session underneath is resumed with `session/load` or replaced by *New session*. The chat never says when the session underneath changes (New session, an agent, model or folder change, a failed resume); only a rollover's handoff card mentions a fresh conversation ([context and memory](../features/context-and-memory.md)), and one line says when another agent takes over or the bot's own comes back.
- **Agent fallbacks**: when the bot's agent can't answer (out of usage, rate limited, signed out, won't start), the next agent in its list carries the same turn on, told what the last one did; each agent keeps its own session, parked while another answers, and agents rest computer-wide until they recover: [docs/features/agent-fallback.md](../features/agent-fallback.md).
- **Agent processes**: a bot starts its ACP agent when needed and keeps saved conversation identity separate from live resources. At most two sessions are resident per agent. Before another allocation, the host closes an inactive reloadable session or retires the agent and reloads the selected saved conversation. A completed routine releases its session immediately, including when the main chat stays warm or another turn is queued. A resumable agent is also recycled before its ninth allocation, bounding resources an adapter retains outside closed sessions. Reloading a session to refresh Claude's instructions releases the previous allocation first. A failed automatic resume returns an error and retains the saved ID; it never silently creates a new conversation.
- **Retirement and cleanup**: sessions unused for 30 minutes close when supported; when all sessions are idle, the resumable agent retires. Graceful EOF shutdown preserves credential refreshes, then a bounded forced cleanup ends remaining workers. Replacement waits for that allocation's cleanup. On Unix the agent owns a session, so MCP workers in separate process groups are included. Separately detached sessions (for example dev servers) block automatic recycling. On Windows the existing background-work guard conservatively blocks recycling because it cannot distinguish such work; capacity errors preserve conversations rather than exceed the budget. Agents unable to resume also retain existing conversations: finished routine sessions can close, but new allocation is refused when capacity cannot safely be released. No retirement occurs during a prompt or while permissions await an answer.
- **Background jobs**: automatic naming and memory jobs share two slots per host. Their three-minute deadline includes waiting for a slot and all setup phases. Cancellation initiates cleanup, and a slot remains held until that agent's cleanup finishes.

- **Group chats and replies** are host features every client drives through the same methods (`send` with `replyTo`, `createBot {kind: group}`); clients never route, parse mentions or build quotes themselves. A group is a roster row whose members answer in their own sessions (Grok Bot's room turns); a reply stays in its chat and session, its quote read before its text: [docs/features/groups-and-replies.md](../features/groups-and-replies.md).
- **A session that fails** with an internal error its agent gives no category (JSON-RPC `-32603` without `data.errorKind`) is closed right after the turn, when the agent can close and load sessions: Claude's adapter otherwise answers every later prompt on it with "The Claude Agent session has ended". The next message loads it again and the conversation carries on (`acp::may_end_session`).
- **Lead bot**: the host makes the first one per computer (`chat/lead.rs`), and the user may pick another (`setLead`) or delete it; on top of every roster, never hidden; its instructions ask for initiative, the *Check in* routine made with the first runs twice a day, and it opens a call with a turn of its own (`Cmd::Prompt`, no user message): [docs/features/lead-bot.md](../features/lead-bot.md).
- Bot collaboration: built-in `team` MCP (`chat/team.rs`) lists visible bots and sends one a request through its actor queue (`message_bot`); nothing waits, and the reply comes back to the sender as a turn of its own in its main chat. Requests and replies are separate turns, bounded by the chain's hop count; native subagents stay with the harness. See [docs/features/bot-collaboration.md](../features/bot-collaboration.md).
- **Context & memory**: frozen instruction snapshot per session + compaction epoch (Claude gets it as a system prompt), profile edits as update blocks, memory in the host (a layer shared by all bots and one per bot, written by the user, the bots' tools and dreaming), busy-time messages folded into one turn or steered into the running one, interrupted turns resumed: [docs/features/context-and-memory.md](../features/context-and-memory.md).
- **Chat shows only**: user messages, the bot's messages (`data.final`: each `send_message` call from the built-in `chat` MCP, Grok Bot's way, also between turns from work the agent goes on with in the background, into the bot's own chat with a *done* alert, unless the user stopped its last turn; a turn that sent none falls back to its last text, unless it reacted to the user's message instead or passed), permission cards, notices. Nothing streams into a bubble; narration, thoughts, tool calls, plans are trace entries (Full conversation sheet; with [Show thinking details](../features/chat-messages.md#while-it-works) on (Settings › Chat), the live activity also unfolds the running turn's steps, without the bot's `bookkeeping` tool calls): [docs/features/chat-messages.md](../features/chat-messages.md).
