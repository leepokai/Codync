# Conversation runtime

- **Chat ≠ session**: a bot is one endless transcript (SQLite `entries`, ordered by `seq`); the ACP session underneath is reopened with `session/load`, or `session/resume` on an agent without it (DeepSeek Harness), or replaced by *New session* (the bot's menu). The chat never says when the session underneath changes (New session, an agent, model or folder change, a failed resume); only a rollover's handoff card mentions a fresh conversation ([context and memory](../features/context-and-memory.md)), and one line says when another agent takes over or the bot's own comes back.
- **Agent fallbacks**: when the bot's agent can't answer (out of usage, rate limited, signed out, won't start), the next agent in its list carries the same turn on, told what the last one did; each agent keeps its own session, parked while another answers, and agents rest computer-wide until they recover: [docs/features/agent-fallback.md](../features/agent-fallback.md).
- **Agent processes**: a bot's agent starts on its first message and keeps its sessions loaded between messages. A session unused for 30 minutes is closed (agents with `session/close`; a routine run's session as soon as the run ends), and once all of them are idle the agent stops with everything it started, as it does right after a routine run when no other session is open; the next message starts it again and reopens the session (`agent/bot/lifecycle.rs`). A routine run's session the agent can't close (Cursor has no `session/close`, or the close failed) goes with the agent instead: it stops as soon as nothing runs or waits, even with the bot's own chat open, and that chat reopens its session on its next turn; otherwise every run would keep a set of MCP servers until the bot sat idle for 30 minutes, which a bot on a short schedule never does. Nothing is released mid-turn or while a queue, approval or request waits. On macOS and Linux an agent leads a session of its own, and stopping it ends every process group in that session, so an MCP server in a group of its own (Codex starts each one so) stops with it (`agent/process.rs`). Agents that can't reopen sessions stay, and so do agents with something running detached in a session of its own, like a dev server from Claude Code's shell tool (stopping the agent would orphan it); MCP servers don't count, even in a process group of their own as Codex starts them, and neither does a session the agent's own program or one of Codync's MCP servers leads, with what runs in it, or a process the agent's program starts to lead a session of its own, without what that one starts (OpenCode 2.x starts its engine, `opencode serve --stdio`, each MCP server and its terminal daemon, `opencode-pty daemon`, that way; they end with the agent). A background command from OpenCode's shell tool runs under that daemon and still holds the agent. A shell or an interpreter as the agent's program (`node`) exempts nothing, and what an MCP server from the user's own agent config starts still holds the agent. Codex keeps a closed session's MCP servers until the agent stops, and codex-acp never closes the thread it titles each new session in ([codex-acp#628](https://github.com/agentclientprotocol/codex-acp/issues/628)), so on Codex only the agent stopping gives them back. Windows has no sessions to tell a dev server from an MCP server, so there the agent's job is checked instead: anything that isn't the agent or Codync's MCP servers holds it, which also keeps an agent with an MCP server from the user's own config or a shell it keeps open, and one with no MCP server left, whose own last process can't be told from a dev server (`agent/bot/background_work.rs`). A dev server the bot starts with `start_dev_server` belongs to the host and doesn't hold the agent ([dev servers](../features/dev-servers.md)). Before a turn on a session an OpenCode 2.x agent already holds, the host checks that one of Codync's MCP servers still runs under it, once it has seen them there: OpenCode drops them after an idle hour, and none left stops the agent and reopens the session in a new process, unless (macOS, Linux) it runs something detached, which keeps it without them until that work ends (`agent/bot/session.rs`, [OpenCode](../upstream-agents/opencode.md)).
- **Group chats and replies** are host features every client drives through the same methods (`send` with `replyTo`, `createBot {kind: group}`); clients never route, parse mentions or build quotes themselves. A group is a roster row whose members answer in their own sessions (Grok Bot's room turns); a reply stays in its chat and session, its quote read before its text: [docs/features/groups-and-replies.md](../features/groups-and-replies.md).
- **A session that fails** with an internal error its agent gives no category (JSON-RPC `-32603` without `data.errorKind`) is closed right after the turn, when the agent can close and reopen sessions: Claude's adapter otherwise answers every later prompt on it with "The Claude Agent session has ended". The next message reopens it and the conversation carries on (`acp::may_end_session`).
- **Lead bot**: the host makes the first one per computer (`chat/lead.rs`), and the user may pick another (`setLead`) or delete it; on top of every roster, never hidden; its instructions ask for initiative, the *Check in* routine made with the first runs twice a day, and it opens a call with a turn of its own (`Cmd::Prompt`, no user message): [docs/features/lead-bot.md](../features/lead-bot.md).
- **Follow-ups**: a bot sets itself one later turn in its own chat (`follow_up` on the `routines` MCP server), to look at something again; when it is due the host starts that turn in the chat's session with the bot's note, and `(pass)` keeps it silent. Routines are the user's standing work, done by a thread of the bot away from the chat, each with a progress note its next run reads: [follow-ups](../features/follow-ups.md), [routines](../features/routines.md#progress-note).
- **Work**: a bot puts long work in its event box as tasks (`add_task` on the `chat` MCP server); threads take them in order, up to the bot's `maxThreads` at once. A thread is where the bot does tasks away from the chat: like the chat it has its own actor, agent process and session (a thread bot, `BotConfig::thread_of`), its session forked from the chat's where the agent can. The chat keeps answering; a thread's approval and choice cards, files and artifacts appear in the chat, and its last message on a task comes back as a turn there (`Cmd::TaskReport`). A routine's run and another bot's request are tasks too (unless the bot uses the computer or manages the team): a run's last message is the routine's message in the chat, a request's is the asking bot's reply: [docs/features/work.md](../features/work.md).
- Bot collaboration: built-in `team` MCP (`chat/team.rs`) lists visible bots and sends one a request, a task in its box (`message_bot`); nothing waits, and the reply comes back to the sender as a turn of its own in its main chat. Requests and replies are separate turns, bounded by the chain's hop count; native subagents stay with the harness. See [docs/features/bot-collaboration.md](../features/bot-collaboration.md).
- **Context & memory**: frozen instruction snapshot per session + compaction epoch (Claude gets it as a system prompt), profile edits as update blocks, memory in the host (a layer shared by all bots and one per bot, written by the user, the bots' tools and dreaming), busy-time messages folded into one turn or steered into the running one, interrupted turns resumed: [docs/features/context-and-memory.md](../features/context-and-memory.md).
- **Chat shows only**: user messages, the bot's messages (`data.final`: each `send_message` call from the built-in `chat` MCP, Grok Bot's way, also between turns from work the agent goes on with in the background, into the bot's own chat with a *done* alert, unless the user stopped its last turn; a turn that sent none falls back to its last text, unless it reacted to the user's message instead or passed), permission cards, notices. Nothing streams into a bubble; narration, thoughts, tool calls, plans are trace entries (Full conversation sheet; with [Show thinking details](../features/chat-messages.md#while-it-works) on (Settings › Chat), the live activity also unfolds the running turn's steps, without the bot's `bookkeeping` tool calls): [docs/features/chat-messages.md](../features/chat-messages.md).
